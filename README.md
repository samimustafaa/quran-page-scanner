# Mus’haf Scan

Android and iOS Quran page scanner, with an entirely Albanian interface. Built by Sami Mustafa.

## What is implemented

- Camera capture and photo-library selection, with a preview before sending.
- Arabic OCR via a private FastAPI service and Google Cloud Vision.
- Conservative text matching to the 604-page Madinah Quran. Low-confidence matches offer possible pages for manual inspection. Photograph ONE page at a time.
- Full-page Albanian translation by **Sherif Ahmeti** (`sq.ahmeti`), retrieved by ayah identity, never generated by a language model.
- All surahs and juz present on a page, ayah references, optional Arabic, adjustable text size.
- All 604 pages / 6,236 ayahs bundled for offline manual reading, bookmarks and recent pages saved on the device.
- Expo Updates integration: compatible updates download in the background on launch and apply on the next cold launch. It does not interrupt reading. Native/runtime changes need a new store build.

**Status:** source implementation, not a published or signed mobile release. OCR needs a Google Cloud Vision credential and a deployed HTTPS backend. EAS builds/updates need an Expo project. Apple distribution needs an Apple developer account. Real photo accuracy and native camera permissions must be tested on devices before release; automated OCR integration tests mock Google's response.

Page boundaries follow the 604-page Madinah edition. A different printed layout cannot be promised the same page number or exact printed-page content. The app explicitly labels this limitation. Multiple-surah and multiple-juz pages are supported.

## Deploy the scanner on Render

1. In Render choose **New → Blueprint**, connect `samimustafaa/quran-page-scanner`, and select `main`.
2. Render reads the included `render.yaml`. Enter `GOOGLE_VISION_API_KEY` when prompted; keep this secret in Render.
3. Create the service and wait for the deployment. The Docker service reads Render's `PORT` automatically and uses `/health` for health checks.
4. Open `https://YOUR-SERVICE.onrender.com/health`. It should report `ok: true`, `pages: 604`, and `scannerConfigured: true`.
5. Use the service's HTTPS URL (without `/health`) as `EXPO_PUBLIC_API_URL` in the mobile app and the EAS preview/production environments.

If using **New → Web Service** manually, select Docker, set Dockerfile path to `./server/Dockerfile`, Docker build context to `./server`, leave Root Directory empty, and set Health Check Path to `/health`. Add `GOOGLE_VISION_API_KEY` in the Environment panel. No database or persistent disk is required.

The Blueprint uses Render's free plan for initial testing. If that plan is unavailable to your account, select an available plan in Render. Free-service cold starts can delay the first scan; open `/health` and wait for a response before testing after inactivity.

## 1. Run the backend locally

Python 3.12 recommended. From `server`:

```sh
python -m pip install -r requirements.txt
# Set GOOGLE_VISION_API_KEY in your environment, NOT in the mobile app.
python -m uvicorn main:app --host 0.0.0.0 --port 8000 --no-access-log --no-proxy-headers
```

On Windows PowerShell, set the key with `$env:GOOGLE_VISION_API_KEY="your-key"` before starting the service. Enable Google Cloud Vision API in your Google Cloud project and restrict the key to that API. Billing may be required.

`GET /health` reports corpus count and scanner configuration. `POST /v1/scan` takes multipart field `image`. `GET /v1/pages/42` returns canonical page data.

For deployment, build `server/Dockerfile` with `server` as the Docker build context. Provide the key through the hosting provider's secret settings. Use HTTPS, a 10 MB request limit at the reverse proxy, request timeouts and an edge rate limit. The built-in IP limiter is per process, is not a replacement for an edge limiter, and uses the direct peer address with proxy trust disabled. Configure trusted proxy forwarding and shared rate limiting for multi-instance deployments. Set `ALLOWED_ORIGINS` for any web preview domain; native apps do not use browser CORS.

No photos or extracted text are stored by this code. Images are decoded, re-encoded to remove EXIF/location metadata, then sent to Google Cloud Vision. Google processing is subject to Google's terms. UI disclosure appears before transmission. Do not enable request-body logging in your hosting/monitoring provider.

## 2. Run the mobile app

Node 24 recommended. From the project root:

```sh
npm ci
```

Copy `.env.example` to `.env` and set `EXPO_PUBLIC_API_URL` to the backend's reachable URL. A real phone must use your computer's LAN IP for local testing (for example `http://192.168.1.20:8000`), never localhost. Use a trusted HTTPS tunnel if device security blocks local HTTP. Production must use HTTPS.

```sh
npm start
```

Open in the matching Expo Go version on Android/iOS for initial testing, or use a development build if required by your installed Expo Go SDK. Expo Go does not test production OTA updates. Manual page reading works even when the scanner URL is not configured. No secret belongs in `EXPO_PUBLIC_*` variables.

```sh
npm run web
```

The web build is a UI/reader preview; native permission dialogs and native update installation still need device tests.

## 3. Create installable builds and enable updates

1. Run `npx eas-cli@latest login` and `npx eas-cli@latest init`. Create/select your Expo project. If the CLI cannot edit the dynamic app config, copy the printed project UUID into `project.config.json` as `easProjectId`. This UUID is public configuration.
2. In EAS, set `EXPO_PUBLIC_API_URL` to the same reachable HTTPS backend for both `preview` and `production` environments. Keep the Google key only on the backend.
3. Verify `npx expo config --type public` shows `updates.enabled: true`, the expected `updates.url`, `extra.eas.projectId`, and bundle identifiers. Change the bundle IDs in `app.config.ts` if you own a different namespace.
4. Run `npm run build:android` to build a shareable Android preview APK through EAS. Use `npx eas-cli@latest build --platform android --profile production` for the Google Play AAB.
5. Run `npm run build:ios` for an iOS store build. EAS prompts for Apple signing. For iPhone internal distribution, use the preview profile and register test-device UDIDs; an unsigned IPA cannot simply be installed like an Android APK.
6. Install a preview build and test both camera and photo-library flows. Publish a small preview update with `npm run update:preview -- --message "Test update"`. Launch to download, then close/reopen to apply.
7. Publish compatible production changes with `npm run update:production -- --message "Release notes"`. Update checks happen once per cold start. Offline devices keep the embedded/cached version.

A GitHub Actions update workflow is included. After configuration, pushes to `main` publish to the production update channel; it can also be run manually for preview or production. Configure `EXPO_TOKEN` as a repository secret and `EXPO_PUBLIC_API_URL` as a repository variable, and commit `project.config.json`. Test on `preview` before choosing `production`. Keep `main` protected and merge only verified mobile changes. A fingerprint runtime policy prevents incompatible native updates from reaching older builds; changed native dependencies require a new signed build. Test OTA rollback/recovery on real preview builds before a public rollout.

## Verification

```sh
npm run typecheck
npx expo export --platform android --platform ios
npm run export:web
python -m pytest -q
```

Python tests cover corpus integrity, full/partial page matching, short/common/unrelated text, ambiguous two-page images, invalid page numbers, invalid uploads, missing configuration, and the multipart scan response with mocked OCR. These checks do not establish a real-world OCR accuracy percentage. Test real printed photos, blur, shadows, rotation, and different phones before publishing.
